# Лабораторная работа №7 по ООП — «Асинхронное программирование»

**Вариант 10.** Проект реализует автоматическую трёхпоточную симуляцию перемещения и боёв NPC на карте 100 × 100. Это самостоятельный проект C++20: модель NPC, фабрика, наблюдатели и инфраструктура редактора находятся внутри этого каталога и не зависят от лабораторной №6.

## Цель работы

Изучить асинхронное выполнение с помощью `std::thread`, организовать безопасный обмен боевыми задачами через `std::condition_variable`, защитить разделяемое состояние мира и консоль, а также корректно остановить и соединить потоки.

## Правила и параметры варианта 10

Атака возможна только при выполнении обоих условий:

```text
attacker.canKill(defender)
    && distance(attacker, defender) <= attacker.killDistance()
```

Допустимые направления атаки:

- Разбойник убивает Оборотня;
- Оборотень убивает Разбойника;
- Орк убивает Разбойника;
- все остальные сочетания не приводят к атаке.

| NPC | Символ | Расстояние хода | Расстояние убийства |
|---|---:|---:|---:|
| Разбойник (`Robber`) | `R` | 10 | 10 |
| Орк (`Orc`) | `O` | 20 | 10 |
| Оборотень (`Werewolf`) | `W` | 40 | 5 |

Для каждого допустимого направления независимо бросаются два шестигранных кубика: атака и защита. Жертва погибает только при `attack > defense`. Если Разбойник и Оборотень могут атаковать друг друга, рассчитываются оба направления на основании состояния в начале боя, поэтому возможна взаимная гибель.

## Начальные параметры

- ровно **50 NPC** случайных типов с уникальными именами;
- случайные целые координаты от 0 до 100 по каждой оси;
- карта **100 × 100**;
- продолжительность основной игры **30 секунд**;
- шаг перемещения по умолчанию — 100 мс;
- вывод карты — раз в 1000 мс;
- журнал убийств — `log.txt` в рабочем каталоге программы.

Для тестов длительность, шаг, число NPC и seed вынесены в `SimulationConfig`. Дополнительный флаг `movementEnabled` позволяет зафиксировать координаты в одном детерминированном тесте; в обычной игре он равен `true`.

## Сборка

Команды для Windows PowerShell или CMD из корня проекта:

```bat
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
```

В Git Bash команды те же. Для другого генератора можно опустить `-G Ninja`.

Реальное имя демонстрационного исполняемого файла — **`lab7_async.exe`** на Windows (`lab7_async` на Linux). Запуск основной 30-секундной игры:

```bat
.\build\lab7_async.exe
```

Короткий запуск с фиксированным seed:

```bat
.\build\lab7_async.exe --duration-ms 2000 --step-ms 50 --count 50 --seed 42
```

Запуск без печати полной карты:

```bat
.\build\lab7_async.exe --duration-ms 2000 --no-map
```

Дополнительные параметры: `--log PATH` выбирает файл журнала, `--help` печатает справку. Пустой путь журнала отключает файлового наблюдателя. Параметры командной строки не меняют продакшен-значения по умолчанию.

## Три потока и их взаимодействие

1. **Поток перемещения и обнаружения** периодически получает собственный `std::mt19937`, перемещает всех живых NPC в одном из четырёх направлений и ограничивает координаты картой. Затем он просматривает пары живых NPC и ставит подходящие пары в очередь.
2. **Поток боёв** спит на `std::condition_variable`, пока очередь пуста. Полученную задачу он проверяет повторно: объекты должны существовать, оба NPC должны быть живы, а дистанция и правила должны допускать атаку. После боя он снимает ключ пары со множества активных задач и отправляет события наблюдателям.
3. **Основной поток** запускает рабочие потоки, раз в секунду печатает снимок карты, по истечении длительности устанавливает флаг остановки, будит ожидающие потоки, выполняет `join()` и печатает выживших.

NPC хранятся в `std::shared_ptr` до завершения симуляции. Смерть не удаляет объект, а только меняет флаг под эксклюзивной блокировкой мира.

## Очередь боевых задач

`BattleQueue` содержит `std::deque<BattleTask>`, `std::set<BattleKey>`, mutex и condition variable. Ключ — лексикографически упорядоченная пара уникальных имён. Он добавляется при постановке и остаётся активным, пока бой не обработан. Поэтому повторная постановка той же пары в любом порядке участников отклоняется.

`pop()` использует предикат `stopped || !tasks.empty()`. После `stop()` новые задачи не принимаются, уже поставленные обрабатываются, а пустая очередь возвращает `std::nullopt`, что завершает боевой поток без активного ожидания.

## Схема синхронизации

- `std::shared_mutex world.mutex_` защищает координаты и состояния всех NPC;
- `std::shared_lock` применяется при поиске пар и создании снимков для карты/выживших;
- `std::lock_guard` применяется при перемещении и расчёте боя;
- отдельный `std::mutex outputMutex_` и `std::lock_guard` защищают каждый консольный вывод;
- отдельные `std::mutex` и `std::condition_variable` защищают очередь;
- `std::atomic<bool> stopRequested_` хранит флаг завершения;
- вторая condition variable позволяет сразу разбудить периодически ожидающие потоки при остановке;
- случайные генераторы не разделяются между потоками;
- наблюдатели вызываются после освобождения mutex мира, а очередь не удерживается во время боя. Это исключает вложенный захват этих mutex и разнобой в их порядке.

## Формат карты и журнала

Карта — текстовая сетка из 101 строки по 101 символу: каждая позиция соответствует целым координатам `(x, y)`, верхняя строка — `y = 100`. Точка обозначает пустую клетку, `R`, `O`, `W` — живых NPC. Мёртвые не отображаются. Если несколько NPC занимают одну клетку, виден символ последнего из них в порядке списка; полный список выживших после игры не теряет такие объекты.

Строка `log.txt` имеет вид:

```text
[KILL] Robber Robber_3 killed Werewolf Werewolf_8 at (42, 17)
```

Координаты в событии относятся к погибшему NPC на момент боя. Консольный наблюдатель выводит тот же формат.

**ThreadSanitizer.** Нативный MinGW не имеет библиотеки `libtsan` (`cannot find -ltsan`). Программа была дополнительно собрана с `-fsanitize=thread` компилятором GCC 11.4 в WSL Ubuntu 22.04, однако runtime TSan до начала симуляции дважды завершился с `FATAL: ThreadSanitizer: unexpected memory mapping`, в том числе с `-no-pie`. Поэтому анализ гонок санитайзером в этой среде не выполнен и отсутствие гонок им не подтверждается.

На проверочной машине Windows Device Guard иногда временно блокировал только что созданные неподписанные бинарники до завершения их проверки. После проверки ОС и основная программа, и CTest запускались штатно; настройки безопасности не изменялись.
