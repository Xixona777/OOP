# Асинхронное программирование в C++20

## Теоретическая часть к лабораторной работе №7 по ООП

**Тема:** асинхронное программирование.  
**Практический пример:** трёхпоточная симуляция NPC, вариант 10.  
**Язык:** C++20.

## Введение

Асинхронное выполнение позволяет разделить независимые этапы работы программы. В данной лабораторной перемещение NPC, проведение боёв и периодический вывод карты связаны через общее состояние и очередь задач. Такое решение требует не только запуска потоков, но и продуманной синхронизации: иначе возможны гонки данных, зависания и взаимоблокировки.

Документ описывает применённые механизмы стандартной библиотеки C++20 и их конкретную реализацию в проекте. Внешние источники не использовались; изложение основано на семантике соответствующих классов стандарта C++.

## 1. Процессы, потоки и асинхронное выполнение

Процесс — экземпляр выполняемой программы с собственным адресным пространством и системными ресурсами. Поток — последовательность исполнения внутри процесса. Потоки одного процесса разделяют код, глобальные данные и динамическую память, но имеют отдельные стеки и контексты исполнения.

Разделение адресных пространств процессов затрудняет прямой доступ к чужой памяти, а разделение памяти потоками, наоборот, делает обмен данными простым и одновременно опасным. Если два потока обращаются к одному объекту без синхронизации, результат может зависеть от порядка инструкций.

Параллелизм означает одновременное исполнение на нескольких вычислительных ресурсах. Конкурентность — организацию нескольких выполняющихся задач, которые могут чередоваться и на одном ядре. Асинхронная операция не обязана завершиться в момент её вызова: инициатор может продолжать другую работу.

В лабораторной используются три логических потока:

```text
+-----------------------------+
| Поток перемещения           |
| 1. Переместить живых NPC    |
| 2. Найти допустимые пары    |
+--------------+--------------+
               | BattleTask
               v
+--------------+--------------+
| BattleQueue + активные ключи|
+--------------+--------------+
               | condition_variable
               v
+--------------+--------------+       +----------------------+
| Поток боёв                  |------>| Консоль и log.txt    |
| 1. Повторно проверить пару  |       | через Observer       |
| 2. Бросить кубики           |       +----------------------+
| 3. Изменить состояние мира  |
+-----------------------------+

+-----------------------------+
| Основной поток              |
| карта раз в секунду         |
| stop -> notify -> join      |
| список выживших             |
+-----------------------------+
```

## 2. std::thread, лямбды и функторы

`std::thread` представляет поток исполнения. Конструктору можно передать функцию, лямбду или объект с `operator()` и аргументы. Поток начинает работу сразу после создания объекта.

Пример запуска лямбды:

```cpp
std::thread worker([this] {
    movementLoop();
});
```

Лямбда `[this]` сохраняет указатель на объект симуляции. Поэтому объект обязан существовать до завершения потока. Деструктор `Simulation` вызывает `stop()` и `join()`, а все поля, используемые потоками, разрушаются только после тела деструктора.

Функтор — класс с перегруженным оператором вызова:

```cpp
struct Worker {
    void operator()() const {
        // работа потока
    }
};
std::thread thread(Worker{});
```

В проекте выбраны лямбды, поскольку они кратко связывают `std::thread` с методами `movementLoop()` и `combatLoop()`.

`std::thread` нельзя копировать, но можно перемещать. Если поток остаётся joinable при разрушении объекта `std::thread`, вызывается `std::terminate`. Поэтому требуется явный `join()` либо, в других архитектурах, `detach()`. Здесь `detach()` не используется: отсоединённый поток мог бы обратиться к уже разрушенным полям.

## 3. Разделяемые ресурсы и data race

Разделяемый ресурс — данные, доступные нескольким потокам. В проекте к ним относятся:

- вектор NPC, их координаты и состояния «жив/мёртв»;
- очередь боевых задач и множество активных пар;
- поток консольного вывода;
- файл журнала;
- флаг остановки.

Data race возникает, когда потоки выполняют конфликтующие обращения к одной области памяти без упорядочения, хотя бы одно обращение является записью, и операции не атомарны. Гонка данных в C++ означает неопределённое поведение, а не просто случайный результат.

Недопустимая схема:

```cpp
// Без блокировки это data race при одновременном вызове.
npc->setPosition(newPosition);  // один поток
auto position = npc->position(); // другой поток
```

Даже чтение целого `int` нельзя считать безопасным только потому, что процессор выполняет его одной машинной инструкцией. Правила языка требуют синхронизации независимо от размера объекта.

Все поля NPC изменяются и читаются рабочими потоками только при блокировке мира. Снимок `NpcSnapshot` копирует нужные значения, после чего карта формируется уже без обращения к изменяемым объектам.

## 4. std::mutex и std::shared_mutex

`std::mutex` реализует взаимное исключение: критическую секцию выполняет не более одного владельца. Он подходит для эксклюзивного доступа и для защиты очереди.

`std::shared_mutex` допускает два режима:

- эксклюзивная блокировка — один писатель, читателей нет;
- разделяемая блокировка — несколько читателей, писателей нет.

Это удобно при частых чтениях и более редких изменениях. В симуляции карта и поиск пар используют чтение, а движение и смерть NPC — запись.

Схема проекта:

```cpp
// Изменение.
std::lock_guard writeLock(mutex_);
npc->setPosition(next);

// Чтение.
std::shared_lock readLock(mutex_);
auto snapshot = npc->position();
```

Разделяемая блокировка не означает, что чтение можно совмещать с записью. Писатель получает исключительный доступ.

Mutex сам не защищает данные автоматически: все потоки должны соблюдать единый протокол захвата. Прямой доступ к NPC вне `World` допустим в тестах только тогда, когда рабочие потоки ещё не запущены или уже завершены.

## 5. std::lock_guard и std::shared_lock

Ручная пара `lock()`/`unlock()` опасна: ранний выход или исключение может оставить mutex заблокированным. RAII-обёртки освобождают блокировку при выходе из области видимости.

`std::lock_guard` — минимальная владеющая обёртка. Он захватывает mutex в конструкторе и освобождает в деструкторе. Его нельзя копировать и перемещать.

`std::shared_lock` управляет разделяемой блокировкой `std::shared_mutex`. Для `pop()` очереди нужен `std::unique_lock`, поскольку `condition_variable::wait()` временно отпускает и повторно захватывает mutex; `lock_guard` для этого не предназначен.

Пример:

```cpp
{
    std::lock_guard lock(outputMutex_);
    output_ << message;
} // mutex освобождён даже при исключении
```

CTAD позволяет записывать `std::lock_guard lock(mutex_)` без явного аргумента шаблона; это поддерживается C++20.

## 6. Защита std::cout

Форматированный вывод состоит из нескольких операций. Если два потока пишут без общей блокировки, строки могут перемешиваться. Кроме того, не следует полагаться на внутренние детали реализации `std::cout` как на замену синхронизации всего сообщения.

В проекте консольный наблюдатель и печать карты получают один `outputMutex_`. Каждое сообщение печатается внутри отдельной критической секции:

```cpp
const std::string map = MapRenderer::render(world_);
std::lock_guard lock(outputMutex_);
output_ << map << std::flush;
```

Снимок мира создаётся до захвата mutex вывода. Боевой наблюдатель захватывает только mutex вывода и не обращается к миру. Благодаря этому не образуется цикл ожидания «мир → вывод» и «вывод → мир».

`FileObserver` имеет собственный mutex и поток `std::ofstream`. Файл не смешивается с консольным mutex, поскольку это независимый ресурс.

## 7. std::atomic

`std::atomic<bool>` обеспечивает атомарные операции над флагом остановки. В проекте рабочие потоки читают флаг, а основной поток устанавливает его:

```cpp
std::atomic<bool> stopRequested_{false};

stopRequested_.store(true);
while (!stopRequested_.load()) {
    // очередной шаг
}
```

Атомарность означает отсутствие data race для самого флага. Она не делает атомарной составную операцию над другими объектами и не заменяет mutex для координат или очереди.

Флаг выражает намерение завершить работу. Для пробуждения потока, который спит на condition variable, дополнительно необходимо уведомление: изменение atomic само по себе не будит condition variable.

## 8. Producer-consumer на std::condition_variable

Активный опрос пустой очереди расходует процессорное время:

```cpp
// Нежелательно: цикл постоянно проверяет очередь.
while (!stop) {
    if (!queue.empty()) {
        process(queue.front());
    }
}
```

Правильная схема producer-consumer использует mutex, condition variable и предикат. Поток перемещения является producer, боевой поток — consumer.

Producer:

```cpp
{
    std::lock_guard lock(mutex_);
    tasks_.push_back(task);
}
condition_.notify_one();
```

Consumer:

```cpp
std::unique_lock lock(mutex_);
condition_.wait(lock, [this] {
    return stopped_ || !tasks_.empty();
});
```

Предикат необходим по двум причинам:

1. уведомление могло произойти до ожидания, но состояние уже изменено корректно;
2. возможны ложные пробуждения, после которых условие ещё не выполнено.

`wait()` атомарно относительно mutex отпускает блокировку и переводит поток в ожидание. После пробуждения mutex снова захвачен. Поэтому проверка очереди и извлечение задачи защищены от других обращений.

`notify_one()` будит одного consumer при добавлении задачи. `notify_all()` при завершении гарантирует пробуждение всех ожидающих потоков.

## 9. Очередь боевых задач

`BattleTask` содержит два `std::shared_ptr<NPC>`. Владение разделяется с миром, поэтому объект не может быть уничтожен, пока задача обрабатывается. Более того, мир вообще не удаляет NPC до конца симуляции.

Для исключения повторной постановки используется ключ из упорядоченных уникальных имён:

```cpp
using BattleKey = std::pair<std::string, std::string>;
std::set<BattleKey> activeTasks_;
```

Ключ вставляется одновременно с постановкой задачи под одним mutex. Повторный `push()` видит ключ и возвращает `false`. При `pop()` ключ не удаляется: задача уже извлечена, но ещё обрабатывается. `complete()` удаляет ключ только после расчёта боя.

Если оба участника погибли или вышли из дистанции до обработки, бой повторно проверяется и не выполняется. Защита успешна — пара может быть обнаружена на следующем шаге снова, но не дублируется, пока предыдущая задача активна.

При остановке очередь сначала отдаёт уже принятые задачи. Когда очередь пуста и `stopped_ == true`, `pop()` возвращает `std::nullopt`. Новые задачи после остановки отклоняются.

## 10. Взаимоблокировки и порядок захвата mutex

Взаимоблокировка — состояние, при котором потоки бесконечно ждут ресурсы друг друга. Классический пример: поток A захватил mutex 1 и ждёт mutex 2, а поток B захватил mutex 2 и ждёт mutex 1.

Основные способы предотвращения:

- уменьшать число одновременно удерживаемых блокировок;
- устанавливать единый порядок захвата;
- использовать `std::scoped_lock` для одновременного захвата, если это действительно необходимо;
- не вызывать внешний код, пока удерживается внутренний mutex.

В проекте выбран первый и четвёртый варианты. Очередь освобождается до `World::applyBattle()`. Мир освобождается до уведомления наблюдателей. Консольный mutex захватывается только для готовой строки. Таким образом, отсутствует вложенный порядок «очередь → мир → наблюдатель».

Блокировки делают критические секции короткими, но важно не сокращать их за счёт небезопасного доступа. Например, проверка живости и установка смерти выполняются внутри одной эксклюзивной секции боя.

## 11. Корректная остановка и join

Завершение выполняется в определённой последовательности:

1. основной поток устанавливает `stopRequested_`;
2. `BattleQueue::stop()` под mutex устанавливает `stopped_` и вызывает `notify_all()`;
3. `stopCondition_.notify_all()` будит поток перемещения и ожидание основного цикла;
4. поток перемещения завершает текущий шаг и выходит;
5. поток боёв обрабатывает оставшиеся задачи и получает `nullopt`;
6. основной поток вызывает `join()` для обоих рабочих потоков;
7. только после этого формируется итоговый список и разрушаются ресурсы.

Повторные `stop()` безопасны. `join()` проверяет `joinable()`, поэтому повторный вызов не приводит к ошибке. Деструктор повторяет остановку и соединение, если пользователь не запустил полный `run()`.

Нельзя просто установить флаг и сразу выйти из `main`: joinable-потоки вызвали бы `std::terminate`, а отсоединённые потоки могли бы использовать уничтоженные объекты.

## 12. Случайные числа в многопоточной программе

`std::mt19937` — генератор псевдослучайных чисел с изменяемым внутренним состоянием. Одновременный вызов одного генератора из нескольких потоков без синхронизации вызывает data race.

Возможные решения:

- отдельный генератор на поток;
- генератор под mutex;
- заранее сгенерированные независимые последовательности.

Проект использует первый вариант. Фабрика имеет генератор начальной популяции, поток перемещения — собственный генератор, боевой поток — собственный `RandomDice`. Seed основного потока и боевого различаются смешиванием констант.

В продакшене seed по умолчанию получается из `std::random_device`. В тестах seed задаётся явно, а броски кубика заменяются через интерфейс:

```cpp
class IDice {
public:
    virtual ~IDice() = default;
    virtual int roll() = 0;
};
```

Это пример внедрения зависимости: боевой алгоритм не зависит от конкретного источника случайности.

## 13. Шестигранный кубик и attack > defense

`RandomDice` использует `std::uniform_int_distribution<int>(1, 6)`. Распределение отвечает за целые значения от 1 до 6; не следует использовать `generator() % 6 + 1`, поскольку такой способ может добавлять остаточное смещение.

Для одного направления атаки:

```cpp
const int attack = dice.roll();
const int defense = dice.roll();
if (attack > defense) {
    victim.kill();
}
```

При равенстве и при `attack < defense` защита успешна. Строгое сравнение важно: условие `>=` ошибочно приравнивало бы равенство к убийству.

Если обе стороны могут нападать, флаги направлений вычисляются до первого броска. Второе направление рассчитывается даже после смерти первой жертвы в текущем бое. Это моделирует одновременность обмена ударами и допускает гибель обоих NPC. На следующую задачу уже мёртвый участник не попадёт как живой.

## 14. Тестирование многопоточного кода

Многопоточные тесты должны ограничивать недетерминизм. Использованы следующие приёмы:

- миллисекундная длительность вместо 30 секунд;
- короткий интервал шага;
- фиксированный seed;
- фиксированные начальные координаты;
- отключение движения только в тесте сквозного боя;
- `SequenceDice` с заданной последовательностью;
- ожидание `future` с тайм-аутом при проверке пробуждения;
- повторные `stop()` и `join()` для проверки жизненного цикла.

Тесты кубиков проверяют все отношения: `attack > defense`, равенство и `attack < defense`. Отдельный сценарий доказывает возможность взаимной гибели Разбойника и Оборотня. Для очереди проверяется, что ключ остаётся активным после `pop()` и до `complete()`.

Отсутствие зависания проверяется не только успешным возвратом теста, но и сценарием, где consumer заранее спит на пустой очереди, а `stop()` должен разбудить его.

GoogleTest проверяет функциональные требования, но не доказывает отсутствие всех гонок. Дополнительно полезны ThreadSanitizer, повторные прогоны и разные планировки нагрузки. Результат санитайзера следует сообщать только при фактически выполненной проверке.

## 15. Применение теории в проекте

| Теоретический механизм | Место применения |
|---|---|
| `std::thread` и лямбды | запуск `movementLoop` и `combatLoop` |
| `std::shared_mutex` | состояние всех NPC в `World` |
| `std::shared_lock` | снимки и обнаружение пар |
| `std::lock_guard` | движение, бой, очередь, вывод |
| `std::unique_lock` | ожидание condition variable |
| `std::condition_variable` | очередь и периодическое ожидание |
| `std::atomic<bool>` | запрос остановки |
| `std::shared_ptr` | время жизни NPC в мире и задачах |
| producer-consumer | передача `BattleTask` между рабочими потоками |
| Observer | консольный и файловый журнал убийств |
| внедрение `IDice` | детерминированные боевые тесты |

Принцип единственной ответственности проявляется в разделении классов: `World` не печатает карту, `BattleQueue` не проводит бой, `MapRenderer` не меняет мир, а `Simulation` управляет жизненным циклом потоков.

## 16. Правила и параметры именно варианта 10

Разрешённые отношения:

| Атакующий | Цель |
|---|---|
| Разбойник | Оборотень |
| Оборотень | Разбойник |
| Орк | Разбойник |

Нет атак Орка на Оборотня, Оборотня на Орка, Разбойника на Орка, а также атак между NPC одного типа.

| Тип | Ход | Дистанция убийства |
|---|---:|---:|
| Разбойник | 10 | 10 |
| Орк | 20 | 10 |
| Оборотень | 40 | 5 |

Евклидово расстояние вычисляется как `sqrt(dx² + dy²)`. Проверка включает границу: расстояние, ровно равное kill distance, допускает атаку. Поиск пары и фактический бой выполняют одну и ту же проверку.

Начальная игра создаёт 50 NPC на координатной плоскости 100 × 100 и длится 30 секунд. Движение возможно вверх, вправо, вниз или влево. У границы новая координата ограничивается диапазоном `[0, 100]`, поэтому фактический ход может быть короче типового расстояния. Мёртвые NPC не перемещаются и не печатаются.

## 17. Контрольные вопросы с краткими ответами

**1. Чем поток отличается от процесса?**  
Поток исполняется внутри процесса и разделяет его адресное пространство; процессы изолированы друг от друга на уровне памяти.

**2. Почему нельзя читать NPC во время записи координат без блокировки?**  
Это конфликтующие неатомарные обращения без упорядочения, то есть data race и неопределённое поведение.

**3. Когда полезен `std::shared_mutex`?**  
Когда независимых чтений много, а изменения требуют редкого исключительного доступа.

**4. Чем `std::lock_guard` отличается от `std::unique_lock`?**  
`lock_guard` — простая неперемещаемая RAII-обёртка; `unique_lock` поддерживает отложенный захват, разблокировку и ожидание condition variable.

**5. Зачем отдельный mutex для `std::cout`?**  
Чтобы сообщения разных потоков не перемешивались на уровне отдельных операций вывода.

**6. Заменяет ли atomic все остальные блокировки?**  
Нет. Atomic защищает отдельный объект, но не составной инвариант мира или очереди.

**7. Почему `condition_variable::wait()` вызывается с предикатом?**  
Предикат правильно обрабатывает ложные пробуждения и повторно проверяет состояние после захвата mutex.

**8. Как исключены дубликаты боевых задач?**  
Активный упорядоченный ключ пары хранится от `push()` до `complete()` под защитой mutex очереди.

**9. Почему нельзя удалить NPC при получении задачи?**  
Задача и мир могут одновременно владеть указателями на него. Здесь объекты живут до конца игры, а смерть является состоянием.

**10. Как предотвращены взаимоблокировки?**  
Очередь, мир и наблюдатели не удерживают вложенные блокировки; внешние уведомления выполняются после освобождения мира.

**11. Что делает `join()`?**  
Блокирует вызывающий поток до завершения рабочего потока, после чего ресурсы можно безопасно разрушать.

**12. Почему после stop нужен `notify_all()`?**  
Atomic не пробуждает ожидание; без уведомления consumer мог бы остаться спящим на пустой очереди.

**13. Можно ли использовать один `std::mt19937` во всех потоках?**  
Только с синхронизацией. В проекте каждый рабочий поток имеет отдельный генератор.

**14. Что происходит при равных кубиках?**  
Защита успешна: убийство требует строгого `attack > defense`.

**15. Как возможна взаимная гибель?**  
Допустимость обоих направлений фиксируется в начале боя, после чего рассчитываются обе атаки независимо от первой смерти.

**16. Почему тесты не запускают 30-секундную игру?**  
Длительность и интервалы настраиваются, а детерминированные входные данные делают проверки быстрыми и воспроизводимыми.

**17. Доказывают ли тесты отсутствие любых гонок?**  
Нет. Они проверяют сценарии; анализ гонок дополнительно выполняют инструментами вроде ThreadSanitizer.

**18. Почему не используется `detach()`?**  
Отсоединённые потоки сложнее безопасно завершить, и они могут обратиться к полям уже разрушенной симуляции.

## Заключение

Асинхронная программа требует проектирования не только алгоритмов, но и владения данными, блокировок и завершения. В лабораторной реализована модель producer-consumer, чтение мира через разделяемые блокировки, эксклюзивные изменения, синхронизированный вывод и управляемая остановка.

Выбор хранения NPC до конца симуляции устраняет опасность висячих идентификаторов, а внедрение источника кубика делает боевую логику проверяемой. Правила варианта 10 отделены от очереди и планирования, поэтому их можно тестировать независимо от случайного хода полной игры. Полученная архитектура демонстрирует практическое применение потоков C++20 без активного опроса и coroutine-замены обязательной трёхпоточной модели.
