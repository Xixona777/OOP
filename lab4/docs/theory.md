## 1. Метапрограммирование и шаблоны

Метапрограммирование в C++ означает выполнение части работы во время компиляции: выбор кода по свойствам типов, проверку ограничений и создание специализаций алгоритмов. Шаблон не является одной обычной функцией или одним классом. Это правило, по которому компилятор создаёт конкретные сущности для заданных аргументов.

Шаблоны позволяют записать алгоритм один раз, не теряя статическую типизацию. Например, координаты точки могут иметь тип `int` или `double`, но структура точки и операции с ней остаются одинаковыми. В отличие от текстового макроса, шаблон понимает типы, области видимости и правила перегрузки.

### Шаблон класса

```cpp
template<class T>
struct Point {
    T x{};
    T y{};
};

Point<int> a{1, 2};
Point<double> b{1.5, 2.5};
```

Здесь `T` — параметр типа. Объявления `a` и `b` используют разные результаты инстанцирования. Их нельзя считать одним типом: `Point<int>` и `Point<double>` несовместимы без явно написанного преобразования.

Шаблон может иметь не только типовые, но и нетиповые параметры. В проекте число вершин `N` является нетиповым параметром `std::size_t`:

```cpp
template<Scalar T, std::size_t N>
class RegularPolygon : public Figure<T> {
    std::array<std::unique_ptr<Point<T>>, N> vertices_;
};
```

Благодаря этому размер массива известен во время компиляции, а `RegularPolygon<double, 6>` и `RegularPolygon<double, 8>` имеют разные типы.

### Шаблон функции

```cpp
template<class T>
T midpoint(T a, T b) {
    return (a + b) / 2;
}

auto x = midpoint(2.0, 4.0);
```

Компилятор выводит `T` из аргументов вызова. Для шаблонных операторов потоков в проекте параметр `T` выводится из `Figure<T>`:

```cpp
template<Scalar T>
std::ostream& operator<<(std::ostream& output,
                         const Figure<T>& figure) {
    figure.print(output);
    return output;
}
```

Оператор не знает конкретный вид фигуры. Он делегирует вывод виртуальной функции `print`, сочетая статическую параметризацию типом координат и динамический полиморфизм вида фигуры.

## 2. Инстанцирование шаблонов

Инстанцирование — создание конкретного определения из шаблона. При неявном инстанцировании компилятор делает это тогда, когда встречает использование, требующее полного типа или вызова функции.

```cpp
Hexagon<int> a;
Hexagon<double> b;
```

Для этих объектов генерируются разные специализации. Компилятор подставляет аргумент, проверяет ограничения и компилирует используемые функции. Важно понимать, что ошибка внутри шаблонной функции может проявиться только при её инстанцировании, а не при первом разборе объявления.

Явное инстанцирование записывается отдельно и иногда применяется, чтобы сократить повторную компиляцию:

```cpp
template class Point<double>;
```

В данном проекте явные инстанцирования не нужны: определения доступны в заголовках, а набор используемых типов невелик. Это проще и не требует обновлять список инстанцирований при появлении нового допустимого скалярного типа.

Шаблонная функция-член обычно инстанцируется лишь при использовании. Поэтому качественные тесты должны не только создавать объект, но и вызывать копирование, присваивание, ввод, клонирование и другие операции. Именно такой набор проверок включён в лабораторную работу.

## 3. Почему реализация шаблонов размещается в заголовках

При обычном разделении класса объявление находится в `.hpp`, а определения функций — в `.cpp`. Для шаблона такой подход по умолчанию недостаточен. Во время компиляции файла пользователя компилятор должен видеть полное тело шаблонной функции, чтобы создать нужную специализацию.

Если определение скрыто в отдельном `.cpp`, файл пользователя может скомпилироваться, но компоновщик не найдёт символ нужной специализации. Возникает ошибка связывания, несмотря на синтаксически правильный исходник.

Основные решения:

1. Разместить объявление и определение шаблона в одном заголовке.
2. Включить файл с определениями в конец заголовка.
3. Скрыть определения в `.cpp` и заранее выполнить явные инстанцирования всех поддерживаемых типов.

В проекте выбран первый вариант. `Array`, `Point`, `Figure`, `RegularPolygon` и наследники реализованы преимущественно в `include/`. Директива `#pragma once` предотвращает повторное включение в пределах одной единицы трансляции. Обычная, нешаблонная логика демонстрации находится в `src/Demo.cpp`, поэтому проект остаётся разделённым на модули.

## 4. Concepts, requires и ограничения

До concepts ошибка несовместимого типа часто появлялась глубоко внутри шаблона и порождала длинное сообщение. Concept задаёт именованное требование к аргументу шаблона и позволяет отклонить неподходящий тип на границе интерфейса.

Собственное ограничение проекта:

```cpp
template<class T>
concept Scalar = std::is_scalar_v<T>;
```

`std::is_scalar_v<T>` истинно для скалярных категорий типов, включая арифметические типы. Использование ограничения:

```cpp
template<Scalar T>
struct Point {
    T x{};
    T y{};
};
```

Запись `template<Scalar T>` эквивалентна введению параметра с ограничением `Scalar`. Проверка выполняется на этапе компиляции, без накладных расходов в работающей программе.

Ограничение можно также записать через `requires`:

```cpp
template<class T>
    requires std::is_scalar_v<T>
struct Point {
    T x{};
    T y{};
};
```

Выражение `requires` бывает и составным. Например, можно требовать операцию сложения и конкретный тип результата:

```cpp
template<class T>
concept Addable = requires(T a, T b) {
    { a + b } -> std::convertible_to<T>;
};
```

Для задания достаточно `Scalar`: оно напрямую выражает требование скалярности. Проверки проекта:

```cpp
static_assert(Scalar<int>);
static_assert(Scalar<double>);
static_assert(!Scalar<std::string>);
```

Concept не доказывает корректность всех геометрических операций для каждого скалярного представления и не заменяет тесты. Он формализует именно заданное требование к типу.

## 5. Виртуальные функции в шаблонной иерархии

Шаблон класса и наследование не исключают друг друга. `Figure<T>` является абстрактным базовым классом для каждой фиксированной специализации `T`:

```cpp
template<Scalar T>
class Figure {
public:
    virtual ~Figure() = default;
    virtual Point<double> center() const = 0;
    virtual std::unique_ptr<Figure<T>> clone() const = 0;
    virtual explicit operator double() const = 0;
};
```

`Figure<int>` и `Figure<double>` — разные несвязанные базовые типы. Объект `Hexagon<double>` можно использовать через интерфейс `Figure<double>`, но не через `Figure<int>`.

Виртуальный деструктор необходим при полиморфном владении: уничтожение через базовый интерфейс должно вызывать полный деструктор фактического объекта. Умный указатель сохраняет корректный способ удаления, а виртуальный деструктор является обязательной частью безопасного интерфейса.

`clone` решает проблему виртуального копирования. При наличии ссылки на `Figure<T>` обычный копирующий конструктор вызвать нельзя, поскольку статический тип не содержит информации о конкретном наследнике. Виртуальный `clone` создаёт объект фактического типа:

```cpp
std::unique_ptr<Figure<T>> clone() const override {
    return std::make_unique<Hexagon<T>>(*this);
}
```

Возврат умного указателя сразу передаёт владение вызывающей стороне. Площадь, центр, вывод и сравнение также используют виртуальные вызовы.

## 6. `unique_ptr` и исключительное владение

`std::unique_ptr` представляет исключительное владение объектом. Одновременно только один такой указатель владеет ресурсом. При разрушении владельца ресурс автоматически освобождается, в том числе при выходе из области видимости по исключению.

Копирование `unique_ptr` запрещено, а перемещение разрешено. Это отражено в системе типов: случайно получить двух владельцев одного объекта нельзя.

```cpp
auto point = std::make_unique<Point<double>>();
point->x = 1.5;
auto another = std::move(point);
```

После перемещения прежний владелец пуст, а `another` отвечает за объект. `std::make_unique` создаёт объект и обёртку без отдельного пользовательского освобождения.

В фигуре вершины хранятся именно так:

```cpp
using Vertices =
    std::array<std::unique_ptr<Point<T>>, N>;
Vertices vertices_;
```

Такое хранение выполняет требование задания и делает отношение владения очевидным: фигура владеет всеми своими точками. Массив фиксированной длины не позволяет случайно изменить число вершин.

`unique_ptr` не означает, что копирование всей фигуры невозможно. Оно означает, что стандартное побитовое копирование владельца недопустимо, поэтому разработчик обязан явно определить нужную операцию глубокого копирования.

## 7. Глубокое копирование класса с `unique_ptr`

При поверхностном копировании два объекта ссылались бы на одни и те же вершины. Изменение копии тогда меняло бы оригинал, а двойное освобождение создавало бы дополнительную опасность при ручном владении.

Копирующий конструктор проекта создаёт новую точку для каждой старой:

```cpp
RegularPolygon(const RegularPolygon& other) {
    for (std::size_t i = 0; i < N; ++i) {
        vertices_[i] =
            std::make_unique<Point<T>>(*other.vertices_[i]);
    }
}
```

Значения координат копируются, но владельцы и сами объекты `Point<T>` различны. После копирования изменение `copy.vertex(0)` не меняет `original.vertex(0)`.

Копирующее присваивание нельзя реализовать простым присваиванием массива `unique_ptr`. В проекте сначала создаётся новый массив независимых точек, затем содержимое обменивается:

```cpp
RegularPolygon& operator=(const RegularPolygon& other) {
    if (this != &other) {
        Vertices copy;
        for (std::size_t i = 0; i < N; ++i) {
            copy[i] =
                std::make_unique<Point<T>>(*other.vertices_[i]);
        }
        vertices_.swap(copy);
    }
    return *this;
}
```

Если выделение одной из точек завершится исключением, текущий объект ещё не изменён. После успешного обмена временный массив владеет старыми вершинами и корректно освобождает их. Проверка самоприсваивания избегает лишней работы.

Перемещающие операции могут быть стандартными: массив и `unique_ptr` сами передают владение. Деструктор также не требует ручного освобождения.

## 8. `shared_ptr` и разделяемое владение

`std::shared_ptr` используется, когда ресурсом могут владеть несколько объектов. Обычно связанный управляющий блок хранит счётчик сильных ссылок. Копия увеличивает счётчик, разрушение уменьшает его, а последний владелец освобождает ресурс.

```cpp
auto figure = std::make_shared<Hexagon<double>>();
std::shared_ptr<Figure<double>> base = figure;
```

Здесь `base` обеспечивает полиморфный доступ, а время жизни объекта не зависит от одной локальной переменной. `shared_ptr` подходит для массива фигур, элементы которого копируются и перемещаются как безопасные дескрипторы владения.

Совместное владение фигурой не отменяет глубокое копирование её внутренних вершин. Операция копирования `shared_ptr<Figure<T>>` намеренно создаёт второго владельца той же фигуры. Если нужен независимый объект, применяется `clone`.

`shared_ptr` не следует использовать без причины: если владелец один, более простым и дешевым выбором является `unique_ptr`. В проекте различие намеренное — точки принадлежат одной фигуре, а полиморфные фигуры могут безопасно передаваться между массивами и другими владельцами.

## 9. Особенности `shared_ptr<T[]>`

Специализация `std::shared_ptr<T[]>` предназначена для массива объектов. Она корректно управляет массивом и предоставляет `operator[]`, но не знает логическое число инициализированных элементов. Поэтому размер и ёмкость хранятся отдельно.

```cpp
std::shared_ptr<T[]> data_;
std::size_t size_ = 0;
std::size_t capacity_ = 0;
```

Новый буфер создаётся так:

```cpp
auto newData = std::make_shared<T[]>(newCapacity);
```

`std::make_shared<T[]>` доступен в C++20. Элементы массива инициализируются по умолчанию, поэтому для `Array<Hexagon<int>>` полезен конструктор по умолчанию фигуры. Он создаёт набор пустых по координатам вершин; такой служебный объект не считается введённой геометрически корректной фигурой.

Копирование `shared_ptr<T[]>` само по себе разделяло бы буфер. Однако требования собственного `Array` задают независимую копию контейнера, поэтому копирующий конструктор выделяет новый массив и копирует значения элементов. Умный указатель отвечает за освобождение буфера, а `Array` — за дисциплину размера, ёмкости и операций с элементами.

Это не замена `std::vector`: управление расширением, сдвиг при удалении и проверки индексов реализованы самостоятельно.

## 10. Семантика перемещения и `std::move`

Копирование создаёт независимое значение, а перемещение передаёт ресурсы из существующего объекта. Для владеющих типов это обычно намного дешевле и иногда является единственной возможной операцией.

`std::move` сам по себе ничего не перемещает. Это преобразование выражения к категории rvalue, которое позволяет выбрать перемещающий конструктор или присваивание:

```cpp
newData[i] = std::move(data_[i]);
```

При расширении `Array` старый буфер больше не понадобится, поэтому элементы переносятся, а не копируются. После перемещения объект остаётся корректным, но его конкретное состояние зависит от типа; обычно следует ограничиться разрушением или присваиванием ему нового значения.

Расширение выполняет шаги:

1. Вычислить новую ёмкость: от нуля к одному, затем удвоение.
2. Создать новый `shared_ptr<T[]>`.
3. Переместить каждый старый элемент.
4. Заменить владелец буфера и обновить ёмкость.
5. Добавить новый элемент.

Перемещающий конструктор `Array` передаёт `shared_ptr` и значения размеров, после чего обнуляет размер и ёмкость источника. Это важно: стандартное перемещение целых чисел просто копирует их, поэтому без явного обнуления перемещённый контейнер ошибочно сообщал бы прежний размер.

В тестах `MoveProbe` содержит счётчики копирующих и перемещающих операций. Нулевые счётчики копирования при расширении объективно подтверждают выбор перемещения.

## 11. Собственный `Array<T>`

Интерфейс контейнера включает `push_back` для lvalue и rvalue, удаление по индексу, два `operator[]`, `size`, `capacity` и операции специальных членов.

Доступ и удаление проверяют условие `index < size_`. При нарушении выбрасывается `std::out_of_range`. Ёмкость не уменьшается автоматически при удалении, поэтому повторные вставки не вызывают лишних перераспределений.

Удаление перемещает последующие элементы на одну позицию влево:

```cpp
for (std::size_t i = index; i + 1 < size_; ++i) {
    data_[i] = std::move(data_[i + 1]);
}
--size_;
data_[size_] = T{};
```

Последняя операция очищает неиспользуемый слот. Размер изменяется только после сдвига, а проверка индекса выполняется до изменений.

Копирование массива глубокое относительно буфера: новая ёмкость и отдельные элементы. Для элемента `shared_ptr<Figure<T>>` это означает отдельный буфер, но совместное владение теми же фигурами, что является обычной семантикой копирования `shared_ptr`.

## 12. `Array<std::shared_ptr<Figure<int>>>` и `Array<Hexagon<int>>`

Первый вариант хранит полиморфные дескрипторы:

```cpp
Array<std::shared_ptr<Figure<int>>> figures;
figures.push_back(std::make_shared<Hexagon<int>>());
auto area = static_cast<double>(*figures[0]);
```

Тип элемента — `shared_ptr<Figure<int>>`. Вызовы `center`, `type` и преобразования площади проходят через виртуальный интерфейс. В один такой массив можно поместить разные наследники с одинаковым `T`.

Второй вариант хранит сами конкретные объекты:

```cpp
Array<Hexagon<int>> hexagons;
hexagons.push_back(Hexagon<int>{});
```

Здесь нет динамического полиморфизма: каждый элемент именно `Hexagon<int>`. Буфер создаёт объекты по умолчанию, а копирование контейнера вызывает глубокое копирование каждой фигуры. Этот тест важен, поскольку выявляет проблемы, которые могут остаться незамеченными при хранении только умных указателей.

Геометрическое замечание: невырожденный равносторонний треугольник, правильный шестиугольник и правильный восьмиугольник не могут быть заданы исключительно целочисленными координатами. Например, для равностороннего треугольника отношение высоты к стороне содержит квадратный корень из трёх. Поэтому `int` применяется для демонстрации шаблонов, владения и центра с плавающей точкой, а корректные геометрические примеры используют `double`.

## 13. Вычисления и проверка фигур

Площадь вычисляется по координатам с помощью формулы шнурования:

```text
S = 1/2 * |Σ(x[i] * y[i + 1] - x[i + 1] * y[i])|
```

Индекс следующей вершины берётся по модулю `N`, поэтому последняя вершина соединяется с первой. Формула подходит для любой ориентации обхода, поскольку результат берётся по модулю.

Центр правильного многоугольника совпадает со средним арифметическим его вершин. Суммирование выполняется в расширенном типе, а возвращается `Point<double>`:

```cpp
Point<double> center() const override;
```

Проверка ввода включает:

- ненулевую удвоенную площадь;
- ненулевые векторные произведения смежных рёбер;
- одинаковый знак этих произведений, то есть строгую выпуклость и последовательный обход;
- равенство квадратов всех сторон;
- равенство квадратов диагоналей через одну вершину.

Для выпуклого многоугольника равенство сторон и таких диагоналей обеспечивает равенство соответствующих треугольников и углов, что соответствует правильной фигуре. Сравнения с `double` используют масштабированный допуск, чтобы не отклонять координаты из-за неизбежной ошибки представления.

Ввод выполняется во временный массив. Новые вершины заменяют старые только после успешной проверки. При нечисловом или геометрически неверном вводе устанавливается `failbit`, а исходная фигура сохраняется.

## 14. Почему отказаться от сырых указателей

Сырой указатель не выражает, владеет ли он объектом, кто должен освобождать память и как долго объект существует. При ручном владении возможны утечка, двойное удаление, висячий указатель и удаление не того объекта. Исключения делают ручную дисциплину ещё труднее.

В методичке мог встречаться пример вида `Array<Figure<int>*>`. В этой лабораторной он заменён на:

```cpp
Array<std::shared_ptr<Figure<int>>>
```

Причина не в том, что умный указатель всегда быстрее или универсальнее. **Прямой запрет сырых указателей в текущем задании имеет приоритет над примером из методички.** Кроме соблюдения требования, замена автоматизирует время жизни и позволяет безопасно копировать элементы контейнера.

Внутри фигуры используется `unique_ptr`, поскольку точки не разделяются между независимыми копиями. Внутри `Array` используется требуемый `shared_ptr<T[]>`, а полиморфная демонстрация применяет `shared_ptr<Figure<T>>`. Так вариант владения виден непосредственно в типе.

## 15. Применение теории в проекте

Теоретические механизмы связаны следующим образом:

- `Scalar.hpp` задаёт ограничение через свойство типа на этапе компиляции.
- `Point.hpp` и фигуры демонстрируют инстанцирование для `int` и `double`.
- Заголовочная реализация исключает отсутствие нужных специализаций при связывании.
- `Figure.hpp` задаёт виртуальный интерфейс, включая деструктор и `clone`.
- `RegularPolygon.hpp` объединяет общий код и хранит `unique_ptr` на вершины.
- Наследники реализуют виртуальное клонирование конкретного типа.
- `Array.hpp` реализует собственное хранилище на `shared_ptr<T[]>`, проверки и специальные члены.
- `Demo.cpp` сочетает конкретные и полиморфные массивы, вычисляет общую площадь и обрабатывает ошибки ввода.
- Тесты проверяют не только результат, но и независимость копий и факт перемещения при расширении.

Статический и динамический полиморфизм решают разные задачи. Тип координат выбирается шаблоном во время компиляции, а вид фигуры может выбираться командой пользователя во время выполнения. Их сочетание устраняет дублирование без потери удобства интерфейса.

## 16. Контрольные вопросы и краткие ответы

**1. Что такое инстанцирование шаблона?**  
Создание компилятором конкретной функции или класса из шаблона для указанных аргументов.

**2. Почему тело шаблона обычно помещают в заголовок?**  
Чтобы компилятор видел определение в каждой единице трансляции, где требуется инстанцирование.

**3. Что проверяет concept?**  
Ограничения на аргументы шаблона во время компиляции; в проекте `Scalar` проверяет `std::is_scalar_v<T>`.

**4. Чем `requires` связан с concept?**  
`requires` записывает требование или ограничивает шаблон, а concept даёт набору требований имя.

**5. Можно ли скопировать `unique_ptr`?**  
Нет, его можно только переместить. Для копии фигуры нужно создать новые точки.

**6. Что делает глубокое копирование фигуры?**  
Создаёт отдельные объекты `Point<T>` с теми же координатами, поэтому копия не делит вершины с оригиналом.

**7. Когда подходит `shared_ptr`?**  
Когда владение ресурсом действительно разделяется несколькими объектами.

**8. Хранит ли `shared_ptr<T[]>` размер массива?**  
Нет. Контейнер самостоятельно хранит размер и ёмкость.

**9. Перемещает ли `std::move` объект само по себе?**  
Нет. Оно преобразует выражение к rvalue и позволяет вызвать перемещающую операцию.

**10. Зачем виртуальный `clone`?**  
Чтобы скопировать фактический динамический тип через базовый интерфейс и вернуть безопасного владельца.

**11. Зачем виртуальный деструктор?**  
Для корректного полиморфного разрушения объекта через базовый интерфейс.

**12. Чем два варианта `Array` различаются?**  
Первый хранит полиморфные `shared_ptr`, второй — непосредственно объекты `Hexagon<int>`.

**13. Почему копия `Array` выделяет новый буфер?**  
Иначе копии контейнера разделяли бы элементы и изменение одной было бы видно через другую.

**14. Как проверено перемещение при расширении?**  
Тестовый `MoveProbe` считает операции; копирования равны нулю, перемещающие присваивания выполняются.

**15. Почему не использован пример с сырым указателем из методички?**  
Прямой запрет задания важнее примера; вместо него выбран `shared_ptr<Figure<int>>`.

## 17. Заключение

В работе рассмотрены основы метапрограммирования C++20 на практической задаче. Шаблоны обеспечили единую реализацию для разных скалярных типов, concept сделал ограничение частью интерфейса, а заголовочные определения обеспечили корректное инстанцирование и связывание.

Умные указатели разделили исключительное и разделяемое владение. Глубокое копирование сохранило независимость фигур, перемещение позволило расширять собственный массив без копирования старых элементов. Виртуальные функции обеспечили единый полиморфный интерфейс, а тесты подтвердили вычисления, владение и обработку ошибок.

Итоговый проект показывает, что безопасность ресурсов и обобщённость не являются взаимоисключающими: точные типы, concepts и стандартные владельцы позволяют выразить их одновременно.
