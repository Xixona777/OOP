# Итераторы и аллокаторы

## Теоретическая часть к лабораторной работе №5 по ООП, вариант 8

### 1. Назначение аллокаторов

Аллокатор отделяет логику контейнера от способа получения и освобождения памяти. Контейнеру нужны операции выделения сырой памяти, создания объекта, разрушения объекта и возврата памяти, но ему не обязательно знать, поступает ли память из глобальной кучи, пула, стекового буфера или другого хранилища.

Такое разделение позволяет:

- менять стратегию управления памятью без изменения алгоритма контейнера;
- уменьшать число обращений к системному аллокатору;
- контролировать время жизни и размещение памяти;
- собирать статистику и проверять использование ресурсов;
- применять один контейнер в разных условиях.

Важно различать сырую память и объект. `allocate` возвращает хранилище подходящего размера и выравнивания, но не создаёт в нём `T`. Конструктор вызывается отдельно через `construct`, а деструктор — через `destroy`. В C++20 стандартные контейнеры используют для этого `std::allocator_traits`.

### 2. std::pmr::memory_resource

Полиморфические ресурсы памяти находятся в заголовке `<memory_resource>`. Базовый класс `std::pmr::memory_resource` определяет единый интерфейс источника памяти. В отличие от аллокатора, тип ресурса не является параметром шаблона контейнера: указатель на базовый ресурс можно выбрать во время выполнения.

Открытые методы `allocate`, `deallocate` и `is_equal` вызывают защищённые виртуальные функции:

```cpp
class FixedBlockMemoryResource : public std::pmr::memory_resource {
protected:
    void* do_allocate(std::size_t bytes,
                      std::size_t alignment) override;
    void do_deallocate(void* pointer, std::size_t bytes,
                       std::size_t alignment) override;
    bool do_is_equal(
        const std::pmr::memory_resource& other) const noexcept override;
};
```

`do_allocate` должно вернуть указатель на хранилище не меньше запрошенного размера с заданным выравниванием либо выбросить исключение, обычно `std::bad_alloc`.

`do_deallocate` возвращает ранее выделенный участок. Аргументы размера и выравнивания соответствуют первоначальному запросу. По стандартному контракту указатель обязан быть получен от того же ресурса и ещё не освобождён.

`do_is_equal` определяет, можно ли через один ресурс освобождать память, выделенную другим. Для отдельных фиксированных буферов корректна проверка идентичности `this == &other`: два разных экземпляра не владеют взаимозаменяемой памятью.

### 3. polymorphic_allocator и rebind

`std::pmr::polymorphic_allocator<T>` хранит указатель на `memory_resource`. Его `allocate` и `deallocate` направляют вызовы этому ресурсу. Поэтому список получает ресурс через конструктор и не обязан знать его конкретный класс.

Список хранит элементы не непосредственно, а внутри узлов:

```cpp
struct Node {
    T value;
    Node* next;
};

using allocator_type = std::pmr::polymorphic_allocator<T>;
using node_allocator =
    std::allocator_traits<allocator_type>::rebind_alloc<Node>;
```

Операция `rebind` нужна потому, что аллокатор `T` должен уметь выделять память под другой тип — `Node`. Создание узла выглядит следующим образом:

```cpp
Node* node = node_traits::allocate(allocator_, 1);
try {
    node_traits::construct(allocator_, node, value, next);
} catch (...) {
    node_traits::deallocate(allocator_, node, 1);
    throw;
}
```

При разрушении порядок обратный: сначала `destroy`, затем `deallocate`. Обычный `new` для узлов не нужен и обошёл бы выбранный ресурс.

### 4. Upstream resource

Upstream — вышестоящий ресурс, у которого данный ресурс получает память. Это может быть `std::pmr::new_delete_resource()`, монотонный ресурс или другая реализация `memory_resource`.

В работе upstream вызывается в конструкторе ровно один раз для получения всего буфера. Последующие запросы списка обслуживаются внутри этого буфера. В деструкторе исходный участок возвращается тому же upstream с теми же ёмкостью и выравниванием.

Схема связей:

```text
SinglyLinkedList<T>
        |
        v
polymorphic_allocator<Node>
        |
        v
FixedBlockMemoryResource ---- один раз ----> upstream
        |
        +---- много участков внутри одного буфера
```

### 5. Fixed-block стратегия

Fixed-block в данной работе означает один непрерывный регион фиксированной ёмкости, а не набор участков одинакового размера. Внутри региона создаются переменные по размеру участки. Сведения о них находятся в `std::vector<Block>`:

```cpp
struct Block {
    std::size_t offset;     // смещение от начала буфера
    std::size_t size;       // размер участка
    bool occupied;          // занят или свободен
    std::size_t alignment;  // выравнивание
};
```

Вектор создан со стандартным аллокатором, а не с указателем на сам fixed-block ресурс. Иначе расширение вектора во время `do_allocate` снова вызвало бы `do_allocate`, возникла бы рекурсия, а метаданные занимали бы управляемый ими буфер.

Начальное состояние и пример разбиения:

```text
Сразу после создания:
[ свободно: весь буфер ]

После выделений A и B и освобождения A:
[ A: свободно ][ B: занято ][ свободный остаток ]

Новый небольшой запрос C:
[ C: занято ][ свободно ][ B: занято ][ свободный остаток ]
```

Сам вектор не входит в ёмкость буфера, поэтому статистика ресурса описывает только память, выданную клиентам.

### 6. First-fit

First-fit — стратегия поиска первого свободного участка, который подходит после учёта выравнивания. Алгоритм:

1. Пройти вектор от начала.
2. Пропускать занятые участки.
3. Вычислить смещение, удовлетворяющее выравниванию.
4. Проверить, помещаются ли префикс и запрошенные байты.
5. Пометить найденную часть занятой.
6. Сохранить свободные префикс и суффикс как отдельные участки.

Преимущества — простота и отсутствие дополнительного поиска по всем вариантам. Недостаток — время поиска O(B), где B — число участков, и возможная фрагментация начала буфера. Best-fit выбирал бы наименьший подходящий участок, но потребовал бы полного просмотра и не устранил бы фрагментацию полностью.

### 7. Фрагментация

Внутренняя фрагментация — потери внутри выданного участка. Например, аллокатор с фиксированным размером ячейки 64 байта при запросе 20 байт не сможет использовать оставшиеся 44 байта для другого клиента. В данной реализации размер занятого участка равен запрошенному, поэтому внутренняя фрагментация мала; отдельные потери возможны в свободных префиксах выравнивания, пока они не подойдут другому запросу.

Внешняя фрагментация — ситуация, когда суммарной свободной памяти достаточно, но нет одного непрерывного участка нужного размера:

```text
[ занято ][ 32 свободно ][ занято ][ 32 свободно ][ занято ]
```

Запрос 64 байт завершится неудачей, хотя всего свободно 64 байта. Перемещать занятые объекты нельзя: клиенты уже хранят их адреса. Поэтому уплотнение таким ресурсом не выполняется.

### 8. Coalescing

Coalescing — объединение соседних свободных участков. После освобождения алгоритм сначала объединяет участок со следующим свободным соседом, затем с предыдущим. Размеры складываются, лишние элементы удаляются из вектора.

```text
До:    [ свободно 32 ][ свободно 32 ][ занято ]
После: [ свободно 64          ][ занято ]
```

Объединять можно только смежные по смещению участки. Без coalescing многократные выделения и освобождения постепенно дробили бы буфер и увеличивали внешнюю фрагментацию. Слияние не гарантирует успех любого будущего запроса, поскольку свободные области всё ещё могут быть разделены занятыми.

### 9. Выравнивание памяти

Выравнивание требует, чтобы адрес объекта был кратен определённой степени двойки. Оно связано с требованиями ABI и может повышать эффективность доступа. Для нарушения выравнивания результат может быть непереносимым или неопределённым поведением.

Исходный буфер запрашивается с `alignof(std::max_align_t)`. Для смещения `offset` и выравнивания `alignment` вычисляется добавка:

```cpp
remainder = offset % alignment;
padding = remainder == 0 ? 0 : alignment - remainder;
aligned_offset = offset + padding;
```

Проверка `bytes <= size - padding` выполняется после проверки `padding <= size`, что исключает переполнение при вычитании. Поддерживаются степени двойки не больше `alignof(std::max_align_t)`. Другие значения приводят к `std::bad_alloc`. Сверхвыровненные запросы потребовали бы отдельной стратегии получения исходного буфера.

### 10. Освобождение оставшейся памяти

Деструктор ресурса не обязан вызывать деструкторы пользовательских объектов: ресурс владеет сырым буфером, а не объектами. Он возвращает upstream весь регион целиком, даже если метаданные ещё содержат занятые участки.

Это предотвращает утечку самого буфера, но не делает безопасным преждевременное уничтожение ресурса. Если контейнер продолжит существовать, его деструктор обратится уже к уничтоженному ресурсу. Кроме того, деструкторы неразрушенных объектов не будут вызваны автоматически.

### 11. Однонаправленный связный список

Каждый узел содержит значение и один указатель на следующий узел. Последний узел ссылается на `nullptr`.

```text
head_ -> [ value | next ] -> [ value | next ] -> [ value | next ] -> nullptr
          первый узел                              последний узел
tail_ ------------------------------------------------^
```

Указатель `head_` обеспечивает доступ к началу, `tail_` — добавление в конец за O(1), а счётчик `size_` — получение размера за O(1).

Сложность операций:

- `push_front` — O(1);
- `push_back` при наличии `tail_` — O(1);
- `pop_front` — O(1);
- `front`, `empty`, `size` — O(1);
- `clear` — O(n);
- проход и поиск — O(n);
- глубокое копирование — O(n), не считая стоимости копирования самих `T`.

Доступ по индексу потребовал бы O(n). Удаление следующего узла просто, а удаление предыдущего без дополнительного прохода невозможно, поскольку обратной ссылки нет. По сравнению с массивом список не обеспечивает произвольный доступ и хуже использует кэш, но не требует перемещения элементов при добавлении в начало.

### 12. Категории итераторов

Итератор обобщает указатель и отделяет алгоритм от устройства контейнера. Основные категории стандартных итераторов:

- output — последовательная запись, однопроходный сценарий;
- input — последовательное чтение, обычно однопроходный;
- forward — чтение и запись с multipass;
- bidirectional — forward плюс движение назад;
- random access — постоянное время перехода на произвольное расстояние;
- contiguous — random access, элементы ещё и непрерывны в памяти.

Однонаправленный список естественным образом предоставляет forward-итератор: можно двигаться только через `next`, но сам элемент не исчезает после инкремента копии.

### 13. Forward iterator и multipass

Forward iterator должен быть копируемым, сравнимым, разыменовываемым и инкрементируемым. Для типа также указываются `value_type`, `difference_type`, `pointer`, `reference`, а категория обозначается `std::forward_iterator_tag`. В C++20 можно указать `iterator_concept` и проверить тип концепцией `std::forward_iterator`.

Multipass означает:

- копия итератора независимо продвигается по последовательности;
- если два итератора равны, после инкремента они остаются равны;
- повторный проход от сохранённого `begin()` возможен;
- инкремент одной копии не меняет другую.

```cpp
auto first = list.begin();
auto second = first;
++first;
// second по-прежнему указывает на первый элемент.

auto length = std::distance(list.begin(), list.end());
for (const auto& value : list) {
    // range-for использует begin() и end().
}
```

В реализации итератор хранит только `Node*`, поэтому эти свойства выполняются. Разыменование `end()` и использование итератора удалённого узла запрещены обычным контрактом итераторов.

### 14. RAII и exception safety

RAII связывает владение ресурсом с временем жизни объекта. Деструктор списка вызывает `clear`, деструктор ресурса освобождает буфер, а стандартный вектор сам владеет метаданными.

При создании узла возможны два этапа: выделение сырой памяти и конструирование значения. Если конструктор `T` выбросил исключение, объект узла не создан, но память уже выделена. Блок `catch (...)`, `deallocate` и повторный `throw` возвращают её без подавления исходной ошибки. Таким образом, не происходит утечки узла.

Добавление элемента обеспечивает сильную гарантию: при неудаче исходный список не меняется. Копирующее присваивание создаёт временный глубокий список в том же ресурсе назначения и только затем обменивает содержимое. Если копирование не удалось, назначение остаётся прежним.

Перемещение узлов без выделения безопасно при одном ресурсе. Если ресурсы различаются, освобождать чужие узлы через ресурс назначения нельзя. Поэтому значения перемещаются во вновь выделенные узлы назначения, после чего исходный список очищается.

### 15. Порядок уничтожения контейнера и ресурса

`polymorphic_allocator` не владеет ресурсом, а хранит наблюдающий указатель. Правильная схема:

```cpp
FixedBlockMemoryResource resource(16 * 1024);
{
    SinglyLinkedList<int> list(&resource);
    list.push_back(42);
} // сначала list возвращает все узлы
// затем resource возвращает исходный буфер upstream
```

Обратный порядок привёл бы к использованию уничтоженного ресурса деструктором списка. Тот же принцип относится к любым объектам, чьи аллокаторы ссылаются на ресурс.

### 16. Применение теории в проекте

Проект непосредственно объединяет рассмотренные механизмы:

- `FixedBlockMemoryResource` реализует виртуальный PMR-интерфейс;
- один upstream-запрос создаёт фиксированный регион;
- `std::vector<Block>` хранит смещение, размер, занятость и выравнивание;
- first-fit находит участок, разбиение сохраняет остатки;
- освобождение запускает coalescing;
- `SinglyLinkedList<T>` получает узлы через `rebind_alloc<Node>`;
- `construct` и `destroy` управляют временем жизни значений;
- итераторы проходят compile-time проверку `std::forward_iterator`;
- тестовый counting upstream подтверждает однократное выделение и окончательный возврат буфера;
- тест исключения конструктора значения подтверждает возврат сырой памяти.

Ограничения решения: отсутствие синхронизации потоков, линейный поиск по метаданным, невозможность уплотнения и ограничение выравнивания `alignof(std::max_align_t)`. Это осознанные свойства учебной fixed-block стратегии, а не скрытые предположения.

### 17. Контрольные вопросы и краткие ответы

**1. Чем аллокатор отличается от memory_resource?**  
Аллокатор предоставляет контейнеру типизированный интерфейс и операции работы с объектами. `memory_resource` — полиморфический источник сырой памяти, выбираемый во время выполнения.

**2. Почему нельзя выделять узлы списка аллокатором `T` напрямую?**  
Размер и тип узла отличаются от `T`. Нужен `rebind_alloc<Node>`, чтобы правильно запросить хранилище для `Node`.

**3. Зачем нужен upstream?**  
Он поставляет исходную память ресурсу. В проекте upstream вызывается один раз для буфера и один раз получает его обратно при уничтожении.

**4. Что хранится в метаданных?**  
Смещение от начала буфера, размер, признак занятости и выравнивание каждого участка.

**5. Почему вектор метаданных не использует собственный ресурс?**  
Это исключает рекурсию и отделяет служебную память от управляемого региона.

**6. Что такое first-fit?**  
Выбор первого свободного участка, подходящего по размеру с учётом выравнивания.

**7. Чем внешняя фрагментация отличается от внутренней?**  
Внутренняя — неиспользуемая часть внутри выданного участка; внешняя — свободная память, разделённая занятыми областями.

**8. Что даёт coalescing?**  
Соседние свободные участки снова становятся одной большой непрерывной областью.

**9. Почему ресурс не может просто уплотнить буфер?**  
Перемещение изменило бы адреса объектов и сделало бы недействительными указатели и итераторы клиентов.

**10. Что означает multipass?**  
Независимые копии итератора позволяют повторно проходить одну последовательность без влияния друг на друга.

**11. Почему `destroy` вызывается до `deallocate`?**  
Сначала нужно корректно завершить время жизни объекта, затем можно повторно использовать занимаемое им хранилище.

**12. Что произойдёт при нехватке памяти?**  
`do_allocate` выбросит `std::bad_alloc`; ресурс не станет незаметно запрашивать дополнительные буферы у upstream.

**13. Кто должен уничтожаться первым: список или ресурс?**  
Список. Его деструктор обращается к ресурсу для возврата узлов, поэтому ресурс должен ещё существовать.

### 18. Заключение

PMR разделяет контейнер и стратегию выделения памяти, сохраняя удобный типизированный интерфейс аллокатора. Фиксированный ресурс показывает, как явно управлять регионом, метаданными, выравниванием и фрагментацией. Собственный список демонстрирует создание узлов через `allocator_traits`, безопасное разрушение и реализацию forward-итераторов. Вместе эти компоненты образуют законченную RAII-архитектуру, поведение которой проверяется автоматическими тестами.
