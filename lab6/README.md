# Редактор подземелья — лабораторная работа №6

## Тема, цель и вариант

**Тема:** «Паттерны проектирования».

**Цель:** закрепить принципы SOLID и применить паттерны Factory, Visitor и Observer на примере редактора подземелья.

**Вариант 9.** Реализованы NPC следующих типов:

- `Elf` — эльф;
- `Dragon` — дракон;
- `Druid` — друид.

Правила нападения:

- дракон убивает эльфа;
- эльф убивает друида;
- друид убивает дракона;
- остальные сочетания, включая NPC одного типа, не приводят к убийству.

Проект написан на C++20. Бой детерминирован: случайные числа не используются.

## Зависимости

Для основной программы:

## Сборка

Команды выполняются из корня проекта.

### Windows с MinGW и Ninja

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
```

Получается исполняемый файл `build/dungeon_editor.exe`, тесты — `build/dungeon_tests.exe`.

### Linux или WSL

```bash
cmake -S . -B build-wsl -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build-wsl --parallel
```

Если в WSL установлен только версионированный компилятор `g++-14`, используется точная команда, применённая при проверке этого проекта:

```bash
cmake -S . -B build-wsl -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=g++-14
cmake --build build-wsl --parallel
```

Получается исполняемый файл `build-wsl/dungeon_editor`.

## Команды редактора

Имена типов в командах указываются латиницей и с учётом регистра: `Elf`, `Dragon`, `Druid`.

- `add Elf имя x y` — добавить эльфа;
- `add Dragon имя x y` — добавить дракона;
- `add Druid имя x y` — добавить друида;
- `print` — напечатать тип, имя и координаты каждого NPC;
- `save путь` — сохранить все объекты в текстовый файл;
- `load путь` — полностью загрузить объекты из текстового файла;
- `fight D` — выполнить один боевой цикл с дальностью `D`;
- `exit` — завершить программу.

Ограничения интерфейса: имя не должно быть пустым или содержать пробельные символы; имена уникальны с учётом регистра. Путь к файлу задаётся одним аргументом без пробелов. Координаты должны быть конечными числами в диапазоне `[0, 500]`. Дальность должна быть конечным неотрицательным числом. Ошибки команды, данных или файла выводятся пользователю и не завершают цикл интерпретатора.

## Формат сохранения

Каждая непустая строка содержит ровно четыре поля, разделённые пробельными символами:

```text
тип имя x y
```

Пример:

```text
Elf Legolas 100 100
Dragon Smaug 120 100
Druid Radagast 400 400
```

Пустой файл обозначает пустой редактор. Пустые строки при загрузке пропускаются. Неизвестный тип, отсутствующие или лишние поля, некорректные координаты и повтор имени являются ошибками. Загрузка атомарна относительно содержимого редактора: сначала проверяется весь файл во временный `Dungeon`, и только при полном успехе заменяется текущая коллекция. Поэтому частично загруженные данные не смешиваются с прежним состоянием. Наблюдатели при загрузке сохраняют подписку.

## Готовый демонстрационный ввод

Содержимое `examples/demo_input.txt`:

```text
add Elf Legolas 100 100
add Dragon Smaug 120 100
add Druid Radagast 400 400
print
save demo_dungeon.txt
load demo_dungeon.txt
fight 20
print
exit
```

Ключевой фактический результат:

```text
Saved 3 NPCs to demo_dungeon.txt
Loaded 3 NPCs from demo_dungeon.txt
Dragon Smaug killed Elf Legolas
Battle finished. Killed: 1. Remaining: 2
Dragon Smaug 120 100
Druid Radagast 400 400
```

## Ход выполнения работы

Сначала была спроектирована иерархия `Npc`. Базовый класс хранит общее состояние: тип, имя, координаты и признак жизни. Он проверяет инварианты координат и имени, вычисляет евклидово расстояние и объявляет виртуальные методы диспетчеризации. `Elf`, `Dragon` и `Druid` являются конкретными производными типами. `Dungeon` владеет объектами через `unique_ptr`, контролирует уникальность имён и предоставляет операции редактора, не беря на себя представление событий.

Для создания объектов реализована `NpcFactory`. Оба пути появления NPC — команда `add` и десериализация — вызывают одну и ту же фабрику. Поэтому при загрузке восстанавливаются настоящие `Elf`, `Dragon` и `Druid`, а выбор конструктора не дублируется в интерфейсе и файловом коде.

Сохранение использует документированный построчный формат и повышенную точность записи `double`. При загрузке каждая строка проверяется полностью, включая лишние поля. Временный редактор исключает незаметную частичную загрузку. Ошибка содержит путь и номер строки, а исходная коллекция остаётся без изменений.

Боевые правила сосредоточены в `BattleVisitor`. Два виртуальных вызова выбирают сначала динамический тип нападающего, затем динамический тип защищающегося. Перегруженные `visit` задают таблицу из девяти сочетаний. `Dungeon::fight` перебирает пары по индексам `i < j`, поэтому одна пара не обрабатывается повторно. Для пары в пределах дальности заранее вычисляются атаки обеих сторон, после чего фиксируются смерти. Это допускает одновременную гибель в общем механизме, хотя правила девятого варианта не создают такого исхода. Погибшие удаляются одним `erase_if` после обхода, а не во время использования итераторов.

Для событий реализован `IObserver`, `ConsoleObserver` и `FileObserver`. Первый пишет в переданный поток, второй открывает `log.txt` в режиме добавления и сбрасывает буфер после события. `Dungeon` хранит `weak_ptr`: владельцем наблюдателя остаётся вызывающий код, а уничтоженный наблюдатель не превращается в висячий указатель. На время уведомления активные наблюдатели фиксируются через `shared_ptr`.

Командный интерфейс в `main.cpp` только разбирает строки, вызывает операции `Dungeon` и сообщает об ошибках. В нём нет создания конкретных NPC или боевых правил. Подготовлен отдельный входной сценарий с тремя типами, печатью, сохранением, загрузкой и убийством.

Тестирование оформлено через GoogleTest и CTest. Тесты проверяют фабрику, границы карты, ошибки файлов, восстановление производных типов, атомарность загрузки, расстояние, все разрешённые и запрещённые атаки, границу дальности, отложенное удаление, однократную обработку пары и оба наблюдателя. Файловые тесты создают отдельные временные каталоги и удаляют их после завершения.

В результате получен многомодульный редактор, в котором хранение, создание, боевые правила и представление событий можно развивать независимо. Добавление совершенно нового типа всё равно потребует расширения фабрики и таблицы Visitor; это сознательное ограничение, а не формальное заявление о полностью закрытой для изменений архитектуре.

## Подготовка публичного GitHub-репозитория

1. Создать на GitHub новый пустой публичный репозиторий, например `oop-lab6-dungeon`.
2. В корне проекта выполнить `git init` и убедиться, что `git status` не показывает `build/`, `build-wsl/`, `log.txt` и демонстрационный `demo_dungeon.txt`.
3. Добавить исходники, тесты, `README.md`, `docs/theory.md` и обязательно бинарный `docs/theory.pdf`.
4. Проверить проект ещё раз, затем самостоятельно выполнить commit и push:

```bash
git add .
git commit -m "Implement OOP lab 6 dungeon editor"
git branch -M main
git remote add origin https://github.com/USERNAME/oop-lab6-dungeon.git
git push -u origin main
```

В описании репозитория полезно указать C++20, CMake и тему паттернов. Не следует публиковать каталоги сборки, локальные настройки и файлы журналов.
