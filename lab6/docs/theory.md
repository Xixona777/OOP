# Паттерны проектирования в редакторе подземелья

## Теоретическая часть к лабораторной работе №6 по ООП

**Тема:** паттерны проектирования.  
**Вариант:** 9.  
**Язык реализации:** C++20.  
**Типы NPC:** эльф (`Elf`), дракон (`Dragon`), друид (`Druid`).

## 1. Назначение паттернов проектирования

Паттерн проектирования — это типовой, проверенный способ организации взаимодействия классов и объектов. Паттерн не является готовой библиотекой или фрагментом, который можно механически вставить в любую программу. Он задаёт распределение ответственности, зависимости и способ расширения системы. Конкретную реализацию необходимо приспосабливать к задаче.

Паттерны помогают решать несколько практических задач:

- уменьшать повторение кода;
- отделять стабильную часть алгоритма от изменяемой;
- заменять длинные цепочки проверок полиморфным поведением;
- ослаблять связность между подсистемами;
- давать разработчикам общий словарь: Factory, Visitor, Observer;
- упрощать тестирование отдельных частей программы.

Использование паттерна само по себе не гарантирует качественной архитектуры. Если класс имеет слишком много обязанностей, добавление ещё одного паттерна только усложнит его. Поэтому в данной работе паттерны связаны с конкретными обязанностями: Factory создаёт NPC, Visitor определяет исход атаки, Observer представляет события об убийствах. Хранение объектов и порядок обхода пар остаются ответственностью `Dungeon`.

В варианте 9 действует циклическая система атак:

- дракон может убить эльфа;
- эльф может убить друида;
- друид может убить дракона;
- обратные направления и атаки однотипных NPC не приводят к убийству.

Эти правила несимметричны. Например, при проверке пары «дракон — эльф» сначала рассматривается атака дракона на эльфа, а затем атака эльфа на дракона. Только первая атака успешна.

## 2. Модель NPC и распределение ответственности

Абстрактный класс `Npc` содержит общее состояние персонажа:

- тип `NpcType`;
- уникальное в пределах редактора имя;
- координаты `x` и `y` типа `double`;
- признак жизни.

Конструктор проверяет инварианты: имя непустое и не содержит пробельных символов, координаты конечны и принадлежат отрезку от 0 до 500. Уникальность имени не может быть инвариантом отдельного NPC, потому что для её проверки нужна вся коллекция. Поэтому её контролирует `Dungeon`.

Упрощённое объявление модели выглядит так:

```cpp
class Npc {
public:
    virtual ~Npc() = default;
    virtual void accept(BattleVisitor& visitor) = 0;

    double distanceTo(const Npc& other) const noexcept;
    void kill() noexcept;
};

class Elf final : public Npc { /* диспетчеризация */ };
class Dragon final : public Npc { /* диспетчеризация */ };
class Druid final : public Npc { /* диспетчеризация */ };
```

Деструктор базового класса виртуальный. Это необходимо для корректного удаления производного объекта через указатель `Npc`. Редактор хранит `vector<unique_ptr<Npc>>`: владение объектом однозначно, копирование исключено, освобождение памяти автоматическое.

`Dungeon` отвечает за коллекцию и операции редактора: добавление, печать, сохранение, загрузку, запуск боевого цикла и удаление погибших. Он не превращает события в текст самостоятельно и не содержит таблицу боевой совместимости. Командный интерфейс находится в `main.cpp` и вызывает уже готовые операции.

Такое разделение облегчает тестирование. Например, фабрику можно проверить без интерфейса, боевые правила — без файла сохранения, а `ConsoleObserver` — с помощью `ostringstream` вместо настоящей консоли.

## 3. Factory

### 3.1. Идея паттерна

Factory — порождающий паттерн, который сосредоточивает создание объектов в отдельном компоненте. Клиент сообщает желаемый тип и параметры, а получает объект через базовый интерфейс. Это особенно полезно, когда конкретный класс выбирается во время выполнения.

В редакторе есть два источника новых NPC:

1. команда пользователя `add`;
2. строка файла при загрузке.

Если в обоих местах написать одинаковый `switch`, список конструкторов будет дублироваться. При добавлении нового типа легко изменить один путь и забыть другой. `NpcFactory` устраняет это дублирование:

```cpp
std::unique_ptr<Npc> NpcFactory::create(
    NpcType type, const std::string& name, double x, double y) const {
    switch (type) {
    case NpcType::Elf:
        return std::make_unique<Elf>(name, x, y);
    case NpcType::Dragon:
        return std::make_unique<Dragon>(name, x, y);
    case NpcType::Druid:
        return std::make_unique<Druid>(name, x, y);
    }
    throw std::invalid_argument("Unknown NPC type");
}
```

Дополнительная перегрузка принимает строку `"Elf"`, `"Dragon"` или `"Druid"` и переводит её в `NpcType`. Неизвестная строка вызывает понятное исключение. Обе перегрузки используют один и тот же код создания.

### 3.2. Factory при загрузке

Десериализатор извлекает из строки тип, имя и координаты, но сам не выбирает конструктор:

```cpp
loaded.add(type, name, x, y);
```

Метод `Dungeon::add` вызывает `factory_.create(type, name, x, y)`. В коллекции поэтому оказываются настоящие производные объекты. Проверка `dynamic_cast<Elf*>`, `dynamic_cast<Dragon*>` и `dynamic_cast<Druid*>` после кругового сохранения и загрузки входит в тесты.

Factory не подменяет проверку данных. Конструктор `Npc` проверяет координаты и имя, а `Dungeon` — уникальность имени в коллекции. Так создание объекта и правила его допустимости не смешиваются.

## 4. Сериализация и десериализация

Сериализация — преобразование состояния объекта в форму, пригодную для сохранения или передачи. Десериализация — восстановление объекта из этой формы.

Выбран текстовый формат, в котором каждая непустая строка содержит ровно четыре поля:

```text
тип имя x y
```

Пример файла:

```text
Elf Legolas 100 100
Dragon Smaug 120 100
Druid Radagast 400 400
```

Преимущества формата: его легко читать, исправлять и проверять без специальных утилит. Ограничения: имя не может содержать пробелы, путь в командном интерфейсе задаётся одним аргументом, типы чувствительны к регистру.

При сохранении применяется `setprecision(17)`, чтобы точность `double` не терялась из-за стандартных шести значащих цифр. Пустая коллекция сохраняется как пустой файл. Ошибка открытия или записи файла преобразуется в исключение с сообщением.

При загрузке проверяются:

- удалось ли открыть файл;
- содержит ли строка все четыре поля;
- отсутствуют ли лишние поля;
- известен ли тип;
- корректны ли координаты;
- нет ли повторного имени;
- не произошла ли ошибка чтения.

Важное свойство реализации — атомарность загрузки относительно состояния редактора. Данные сначала добавляются во временный `Dungeon loaded`. Если пятая строка повреждена, первые четыре не попадают в текущий редактор. Только после обработки всего файла выполняется перемещение коллекции:

```cpp
npcs_ = std::move(loaded.npcs_);
```

Подписки наблюдателей при этом не заменяются. Сообщение об ошибке включает путь и номер строки. Таким образом, отсутствует незаметная частичная загрузка.

## 5. Visitor и double dispatch

### 5.1. Задача двух динамических типов

Обычный виртуальный вызов выбирает реализацию по одному динамическому типу. В бою результат зависит сразу от двух типов: нападающего и защищающегося. Если оба объекта доступны как `Npc&`, простого виртуального метода с одним аргументом недостаточно.

Double dispatch означает двукратный полиморфный выбор. Сначала вызывается `accept` нападающего и выбирается перегрузка `visit` для `Elf`, `Dragon` или `Druid`. Затем вызывается `accept` защищающегося с уже известным статическим типом нападающего. Вторая диспетчеризация выбирает перегрузку для пары типов.

Схема вызова:

```text
canKill(attacker, defender)
        |
        v
attacker.accept(visitor)
        |
        v
visitor.visit(ConcreteAttacker&)
        |
        v
defender.accept(visitor, attacker)
        |
        v
visitor.visit(ConcreteAttacker&, ConcreteDefender&)
```

Центральная функция Visitor невелика:

```cpp
bool BattleVisitor::canKill(Npc& attacker, Npc& defender) {
    defender_ = &defender;
    kills_ = false;
    attacker.accept(*this);
    defender_ = nullptr;
    return kills_;
}
```

Правила варианта представлены девятью перегрузками. Три успешные атаки имеют значение `true`:

```cpp
void BattleVisitor::visit(Dragon&, Elf&) noexcept   { kills_ = true; }
void BattleVisitor::visit(Elf&, Druid&) noexcept    { kills_ = true; }
void BattleVisitor::visit(Druid&, Dragon&) noexcept { kills_ = true; }
```

Остальные шесть сочетаний задают `false`. Вся таблица находится в одном файле `BattleVisitor.cpp`, а не разбросана по `main.cpp`, файловым операциям и классам хранения.

### 5.2. Зачем здесь Visitor

Visitor отделяет операцию над элементами иерархии от состояния самих элементов. `Elf` не должен знать всех возможных противников, а `Dragon` не должен содержать ссылки на наблюдателей. Добавление новой операции над иерархией может быть выполнено новым посетителем.

У паттерна есть цена. Добавление нового типа NPC требует новых перегрузок и методов диспетчеризации. Для небольшой стабильной иерархии из трёх типов это приемлемо и делает правила явными. При частом расширении набора классов Visitor может оказаться менее удобным, чем другая таблица правил. Это практический компромисс, который важно учитывать.

## 6. Евклидово расстояние и боевой цикл

Для координат `(x1, y1)` и `(x2, y2)` евклидово расстояние равно:

```text
sqrt((x1 - x2)^2 + (y1 - y2)^2)
```

В C++ используется `std::hypot`:

```cpp
double Npc::distanceTo(const Npc& other) const noexcept {
    return std::hypot(x_ - other.x_, y_ - other.y_);
}
```

`hypot` удобен тем, что выражает смысл формулы непосредственно и устойчив к промежуточным переполнениям лучше наивного вычисления суммы квадратов. Для точек `(0, 0)` и `(3, 4)` расстояние равно 5.

Атака рассматривается, если `distance <= D`. Строгое включение границы проверено отдельным тестом: дракон и эльф на расстоянии 5 взаимодействуют при `D = 5`, но не взаимодействуют при значении, непосредственно меньшем 5. Отрицательная, бесконечная и нечисловая дальность отклоняются.

Пары перебираются следующим образом:

```cpp
for (std::size_t i = 0; i < npcs_.size(); ++i) {
    for (std::size_t j = i + 1; j < npcs_.size(); ++j) {
        // обработка неупорядоченной пары (i, j)
    }
}
```

Условие `j = i + 1` исключает пары NPC с самим собой и повтор `(j, i)`. Для каждой пары в пределах дальности до изменения состояния вычисляются обе атаки:

```cpp
const bool firstKillsSecond = visitor.canKill(first, second);
const bool secondKillsFirst = visitor.canKill(second, first);
```

Затем независимо применяются оба результата. Поэтому общий механизм допускает смерть обоих участников. В правилах варианта 9 такого исхода нет, поскольку для каждой разнотипной пары успешна только одна сторона.

NPC, погибший в ранее обработанной паре, пропускается в дальнейших парах. Смерть фиксируется сразу, но объект остаётся в контейнере до конца обхода. Это позволяет корректно ссылаться на участников при уведомлении и не изменять размер контейнера во время цикла.

## 7. Безопасное удаление погибших

Удаление элемента из `vector` делает недействительными итераторы и ссылки на элементы в изменяемой части контейнера. Если удалять текущий объект внутри вложенного обхода, легко пропустить элемент, выйти за границу или обратиться по недействительной ссылке.

В работе применяется отложенное удаление:

1. во время боя вызывается `kill()`, меняющий только флаг;
2. уведомления получают ссылки на ещё существующие объекты;
3. после обработки всех пар выполняется один `erase_if`;

```cpp
std::erase_if(npcs_, [](const auto& npc) {
    return !npc->isAlive();
});
```

Умные указатели удалённых элементов освобождают память автоматически. Тест `RemovesDeadNpcAfterProcessingPairs` подтверждает, что в момент уведомления размер коллекции ещё равен двум, а после завершения цикла — одному.

## 8. Observer

### 8.1. Подписка и уведомление

Observer определяет зависимость «один ко многим»: при событии источник уведомляет произвольное число подписчиков, не зная деталей их реализации. В редакторе событием является убийство.

Интерфейс содержит одну операцию:

```cpp
class IObserver {
public:
    virtual ~IObserver() = default;
    virtual void onKill(const Npc& killer, const Npc& victim) = 0;
};
```

`ConsoleObserver` выводит сообщение в переданный `ostream`. `FileObserver` открывает файл в режиме `std::ios::app`, то есть добавления, и не затирает предыдущие записи. После каждого события выполняется `flush`, поэтому результат можно сразу прочитать из файла.

Текст события содержит динамические типы и имена обоих участников:

```text
Dragon Smaug killed Elf Legolas
```

Оба наблюдателя подключаются к одному `Dungeon` и получают одно и то же событие. Боевой Visitor не знает о выводе: уведомление выполняет редактор после установления факта смерти.

### 8.2. Время жизни подписчиков

Хранение сырых указателей на наблюдателей опасно: после уничтожения подписчика источник мог бы обратиться по висячему указателю. В реализации коллекция имеет тип `vector<weak_ptr<IObserver>>`.

При уведомлении каждый `weak_ptr` преобразуется в `shared_ptr` с помощью `lock()`. Если объект уже уничтожен, `lock()` возвращает пустой указатель, а запись удаляется из списка. Активные `shared_ptr` сохраняют объекты на всё время цикла уведомлений.

```cpp
if (auto observer = weakObserver.lock()) {
    activeObservers.push_back(std::move(observer));
}
```

Метод `removeObserver` удаляет совпадающего и уже недействительных подписчиков. Владение остаётся у вызывающего кода, а `Dungeon` не продлевает жизнь наблюдателей без необходимости. Тесты проверяют отписку и уничтожение временного наблюдателя до боя.

## 9. Принципы SOLID на примере проекта

SOLID — набор ориентиров для устойчивого объектно-ориентированного проектирования. Ниже принципы связаны с конкретным кодом, а не используются как формальные лозунги.

### 9.1. Single Responsibility Principle

Принцип единственной ответственности требует, чтобы у класса была одна причина для изменения на уровне его роли.

- `Npc` изменяется при изменении состояния и инвариантов персонажа.
- `NpcFactory` — при изменении способа создания типов.
- `Dungeon` — при изменении операций коллекции и порядка боевого цикла.
- `BattleVisitor` — при изменении совместимости атак.
- `ConsoleObserver` и `FileObserver` — при изменении соответствующего представления событий.

Например, изменение формата строки журнала не требует правки таблицы атак. Это конкретный результат разделения ответственности. При этом `Dungeon` объединяет файловые операции и обход коллекции, поэтому в более крупной системе сериализацию можно вынести в отдельный компонент.

### 9.2. Open/Closed Principle

Принцип открытости/закрытости ориентирует на добавление поведения через расширение, а не изменение стабильных клиентов.

Новый способ представления события, например сетевой наблюдатель, можно добавить классом, реализующим `IObserver`. Цикл боя и существующие наблюдатели менять не потребуется. Это реальный пример расширения без модификации источника событий.

Ограничение принципа видно на Visitor: добавление четвёртого типа NPC потребует расширить фабрику, иерархию и перегрузки Visitor. Нельзя честно утверждать, что вся система закрыта для любых изменений. Паттерн делает места расширения явными, но не устраняет все зависимости.

### 9.3. Liskov Substitution Principle

Принцип подстановки Барбары Лисков означает, что производный объект должен сохранять ожидания клиента о базовом типе.

`Dungeon` работает с `Npc&` и `unique_ptr<Npc>`, не проверяя конкретный класс для печати, расстояния или сохранения. Любой из `Elf`, `Dragon`, `Druid` поддерживает одни и те же инварианты координат, имени и состояния. Диспетчеризация меняет результат атаки, но не нарушает общий контракт `Npc`.

Виртуальный деструктор и запрет копирования через базовый тип также поддерживают корректное использование полиморфных объектов.

### 9.4. Interface Segregation Principle

Принцип разделения интерфейсов советует не заставлять клиента зависеть от операций, которые ему не нужны.

`IObserver` содержит только `onKill`: файловому наблюдателю не нужно реализовывать печать списка, сохранение или боевые методы. Публичный интерфейс `NpcFactory` ограничен созданием. Это небольшие целевые интерфейсы.

`BattleVisitor` содержит больше перегрузок, потому что они необходимы для double dispatch. Это не отдельный узкий интерфейс для всех клиентов, а специализированный компонент боевой системы.

### 9.5. Dependency Inversion Principle

Принцип инверсии зависимостей предполагает зависимость высокоуровневой логики от абстракций.

Код боя зависит от `IObserver`, а не от `ConsoleObserver` и `FileObserver`: уведомление вызывается через виртуальный метод. Коллекция NPC полиморфна относительно `Npc`. В тестах консольный наблюдатель заменяется считающим наблюдателем без изменения боя.

В то же время `Dungeon` непосредственно владеет конкретной `NpcFactory` и создаёт конкретный `BattleVisitor`. Для данной небольшой работы это простое решение, но строгая инверсия всех зависимостей не декларируется. При необходимости заменяемых реализаций фабрики или правил их можно передавать через интерфейсы и конструктор.

## 10. Преимущества разделения боевой логики, хранения и вывода

Разделение даёт следующие практические преимущества:

1. **Проверяемость.** Правила атаки тестируются напрямую через `BattleVisitor`, а вывод — через строковый поток и временный файл.
2. **Меньшая связность.** Изменение сообщения журнала не затрагивает обход пар и сохранение.
3. **Повторное использование.** Один бой автоматически уведомляет любое число наблюдателей.
4. **Явные инварианты.** Координаты проверяет NPC, уникальность — коллекция, дальность — боевой метод.
5. **Безопасность владения.** `unique_ptr`, `shared_ptr` и `weak_ptr` выражают разные отношения владения.
6. **Простой интерфейс.** `main.cpp` не содержит создания производных классов и правил совместимости.

Разделение не бесплатно: появляется больше файлов и виртуальных вызовов. Однако здесь каждый компонент имеет самостоятельную роль и отдельно проверяется, поэтому дополнительная структура оправдана.

## 11. Тестирование и обработка ошибок

GoogleTest подключён через CMake, а регистрация тестов выполняется с помощью `gtest_discover_tests`. CTest запускает 31 отдельный тест.

Проверяются следующие группы:

- создание всех типов и ошибка неизвестного типа;
- границы координат 0 и 500, выход за карту, NaN и бесконечность;
- повтор имени и печать списка;
- круговое сохранение с восстановлением производных типов;
- пустой файл, повреждённые строки, лишние поля, ошибки открытия;
- сохранение прежнего состояния после неудачной загрузки;
- евклидово расстояние и точная граница дальности;
- три разрешённые атаки и шесть недопустимых сочетаний;
- отсутствие боя вне дальности и повторной обработки пары;
- отложенное удаление погибших;
- консольное и файловое уведомление, добавление в существующий журнал;
- отписка и истечение `weak_ptr`.

Тесты с файлами получают уникальные каталоги во временной файловой системе. Они не используют общий `log.txt` и не зависят от предыдущих запусков. Каталоги удаляются после каждого теста.

Исключения применяются на границе библиотеки для сообщения об ошибках данных и ввода-вывода. Командный цикл перехватывает `std::exception`, печатает сообщение и продолжает работу. Ошибка неизвестной команды не завершает редактор.

## 12. Контрольные вопросы с краткими ответами

**1. Почему деструктор `Npc` виртуальный?**  
Чтобы удаление через `unique_ptr<Npc>` вызывало деструктор фактического производного объекта и не приводило к неопределённому поведению.

**2. Где проверяется уникальность имени и почему?**  
В `Dungeon`, поскольку для проверки нужна вся коллекция, а не состояние одного NPC.

**3. Какую задачу решает Factory?**  
Сосредоточивает выбор конкретного конструктора и используется одинаково при добавлении и загрузке, исключая дублирование создания.

**4. Почему после загрузки сохраняются производные типы?**  
Фабрика создаёт `Elf`, `Dragon` или `Druid` по полю типа, а коллекция хранит указатели на базовый класс.

**5. Что означает атомарная загрузка?**  
Текущая коллекция заменяется только после полного успешного разбора файла; повреждённая строка не оставляет частично загруженные данные.

**6. Чем double dispatch отличается от обычного виртуального вызова?**  
Реализация выбирается последовательно по динамическим типам двух объектов, а не одного.

**7. Где записаны правила варианта 9?**  
В перегрузках `BattleVisitor::visit`: успешны `Dragon → Elf`, `Elf → Druid`, `Druid → Dragon`; остальные сочетания ложны.

**8. Почему используется `std::hypot`?**  
Он вычисляет евклидово расстояние непосредственно по разностям координат и корректно обрабатывает численные крайние случаи лучше ручной суммы квадратов.

**9. Как гарантируется однократная обработка пары?**  
Вложенный цикл начинается с `j = i + 1`, поэтому пары `(i, j)` и `(j, i)` не обрабатываются дважды.

**10. Почему погибшие не удаляются сразу?**  
Отложенное удаление сохраняет действительными ссылки во время событий и избегает инвалидации итераторов в процессе обхода.

**11. Почему `FileObserver` открывает файл с `std::ios::app`?**  
Режим добавления сохраняет ранее записанные события, а `flush` делает новую запись сразу доступной.

**12. Зачем нужны `weak_ptr` в списке наблюдателей?**  
Они позволяют обнаружить уничтожение наблюдателя и не обращаться по висячему указателю; на время уведомления создаётся `shared_ptr`.

**13. Допускает ли механизм взаимную гибель?**  
Да, обе атаки вычисляются до применения результатов. Но таблица варианта 9 сама по себе не даёт взаимного успешного нападения.

**14. Как Observer связан с Open/Closed Principle?**  
Новый класс подписчика можно подключить через `IObserver`, не изменяя алгоритм боя.

**15. Полностью ли проект закрыт для изменений?**  
Нет. Новый тип NPC потребует изменить фабрику и Visitor. Это явное ограничение выбранной архитектуры.

## Заключение

В лабораторной работе три паттерна применены для разных задач. Factory единообразно создаёт конкретные NPC при работе интерфейса и десериализации. Visitor с double dispatch сосредоточивает таблицу боевой совместимости варианта 9. Observer отделяет консольное и файловое представление событий от боя, а слабые указатели делают подписку безопасной по времени жизни.

Модель дополнена проверкой инвариантов, евклидовой дальностью, однократным обходом пар, отложенным удалением и атомарной загрузкой. Разделение обязанностей позволило покрыть систему 31 независимым тестом и проверить демонстрационный сценарий с реальным убийством. SOLID рассмотрен не как формальная характеристика, а через конкретные примеры и ограничения: расширять наблюдателей просто, а добавление нового типа NPC требует согласованного изменения нескольких компонентов.
